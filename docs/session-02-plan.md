# Session 02 — Plan

Four phases. Each gates the next: no point wiring an orchestrator to a runtime
whose containment is unverified, and no point designing shell access before a
container runs at all.

---

## Phase A — Base image

**Goal:** one locally-built image `praxis/ops-base` that ticket images derive from.

With no registry, build directly into `praxis-sbx`'s store. Everything runs as
that user, from `/` (see the cwd trap in session 01).

Contents, kept minimal — every package is attack surface and every package is
also a tool the candidate might need:

- coreutils, findutils, grep, sed, awk, less, vim-tiny
- procps, psmisc, lsof, strace (troubleshooting is the exercise)
- python3-minimal (fix-c paths in the ticket bundles use it)
- a `candidate` user, uid 1000 inside the container
- `/opt/praxis` for check-script drop-in

Deliberately absent: curl, wget, git, any package manager, any compiler. The
sandbox has no egress, so these are dead weight that only help exfiltration
attempts look plausible.

**Open question that must be settled here:** where the base rootfs comes from.
With registries blocked and zero egress, there is no `FROM ubuntu:24.04`. Three
options, in order of preference:

1. `debootstrap` a minimal rootfs on the host, `podman import` it. Fully local,
   fully reproducible, no registry ever needed.
2. `podman save` an image on a connected machine, `scp` the tar, `podman load`.
   Simple, but the provenance is whatever that other machine had.
3. Relax the egress rule and `policy.json` for one pull, then re-seal. Fastest,
   and the option most likely to be left un-re-sealed by accident.

Recommend (1). It is the only one that keeps "this host can pull from nowhere"
true, which is a claim worth being able to make without an asterisk.

**Done when:** `podman images` as `praxis-sbx` lists the base, and
`podman run --rm praxis/ops-base echo ok` prints `ok`.

## Phase B — Prove containment in the field

**Goal:** turn every configured control into an observed result.

```bash
sudo PRAXIS_VERIFY_IMAGE=praxis/ops-base ./50-verify.sh
```

This runs the half that has never executed: userns host-uid mapping, socket
invisibility, `/proc/kcore`, block devices, mount blocking, DNS, egress, memory
and pids ceilings.

Then `security/hardening-check.sh` **from inside** a container — it overlaps
`50` deliberately, because a control asserted from outside and a control
observed from inside are different evidence.

Also in this phase:

- reboot, re-run `50` — proves the loop mount and nftables include persist
- confirm `user.max_user_namespaces` is back to the kernel default
- verify a fork bomb inside a sandbox hits the pids ceiling rather than the host

**Done when:** `50` passes with the container half included, and the reboot has
happened. Only at this point is the phrase "hardened host" earned.

## Phase C — Shell access and credentials

**This is a new hole in a currently sealed box.** Everything so far assumed no
inbound path to a sandbox. A candidate needs a shell, and how that shell is
delivered is the largest remaining design decision.

### The decision

**Option 1 — `podman exec` proxied by the orchestrator.**
Container keeps `network: none`. No sshd, no port, no netns, no listener. The
orchestrator holds a PTY exec session and relays it to the portal over the
loopback API that already exists. Credentials are portal session tokens; the
sandbox has no credentials at all because there is nothing to authenticate to.

- keeps the entire network hardening intact
- no per-attempt keys, no port allocation, no sshd in the image
- candidate works in a browser terminal, not their own client
- orchestrator grows a websocket relay — real work, and it is on the path
  between an untrusted process and the portal

**Option 2 — real sshd inside each sandbox.**
Matches SadServers: the candidate uses their own terminal, scp works, tooling is
familiar. Costs: sshd in every image, a netns with an address, a published port
per attempt, per-attempt keypair generation and delivery, and an ingress path
through hardening that currently has none.

- higher fidelity to real ops work, which is the point of the product
- meaningfully more surface, and every item above is a place to get it wrong

**Recommendation: Option 1 for the POC.** The POC is about seeing the flow, and
Option 1 gets there without reopening the network model. Revisit Option 2 when
fidelity matters more than blast radius — and treat it as its own hardening
exercise, not an increment.

### If Option 2 is chosen anyway

- per-attempt ed25519 keypair, generated by the orchestrator, private key handed
  to the candidate once and never stored
- authorized_keys injected at spawn, never baked into the image
- sshd bound to the container netns only, published on 127.0.0.1 with a
  per-attempt port; never 0.0.0.0
- `nftables`: inbound to those ports from the gateway only
- key lifetime tied to `expires_at`, revoked by the reaper along with the container

**Done when:** a candidate-equivalent user can obtain a shell in a running
sandbox, and cannot obtain one in a sandbox belonging to a different attempt.

## Phase D — Go orchestrator

Only after A–C. The code from session 01 exists but has never compiled — the
module proxy was unreachable, so `go mod tidy` has not run.

Order:

1. `go mod tidy`, fix whatever moved in the Docker client API between v25 and
   v26 (`types.ExecConfig` and `types.CopyToContainerOptions` are the likely
   candidates). Compile before reading anything else.
2. **Resolve the digest-pinning conflict.** `Runbook.Validate()` requires
   `@sha256:`, which no locally-built image has. Either accept a local image ID
   (still a content hash, still pins) or relax the check. This is a consequence
   of choosing no registry and must be decided, not worked around.
3. Point `DOCKER_HOST` at `/run/user/1001/podman/podman.sock`, spawn and destroy
   a `praxis/ops-base` container by hand through the API.
4. Install the systemd user unit. Confirm the reaper survives a restart and
   rebuilds state from labels alone.
5. Set `PRAXIS_MAX_CONCURRENT=2` — 14G RAM with GitLab taking 4–8G does not
   support three CPT-01 sandboxes at 768m plus systemd overhead.
6. Wire whichever shell transport Phase C settled on.

**Done when:** spawn → exec a check script → destroy runs end to end against a
real ticket image, driven entirely through the HTTP API.

## Still owed from earlier sessions

- **Scoring envelope** — asked for and never delivered. The grader's output
  contract: attempt/session ids, timing (wall vs instance-active), per-assertion
  results, command counts, verdict. Scoring is a pure function of that envelope,
  so the envelope must be stable before any scoring logic exists.
- **Bake pipeline** — `substrate_image` is `REPLACE_AT_BAKE` in all three
  tickets, and SKN-01's `check.sh` carries `__BAKE_EXPECTED_COUNT__` and
  `__BAKE_LOG_SHA256__` placeholders. Nothing runs until something fills them.

Both are Phase A-adjacent: the bake step is what produces the ticket images that
Phase B and D need.
